# crm · план полной автономии

дата: 2026-10-12. проект: `dashhkuns.com/crm-app/`. текущая crm v11.

## цель

вся входящая операционка централизованно попадает в crm и обрабатывается по единому процессу: событие → классификация → проверка правил → исполнение / запрос согласования → подтверждение результата → запись в журнал → уведомление пользователю. никакие нарисованные счётчики или выдуманные «отправлено» не допускаются.

### фактическое состояние на момент аудита

- источник истины supabase: `crm_projects`, `crm_tasks`, `crm_leads`, `crm_messages`, `crm_events`, `crm_alerts`, `crm_operator_actions`, `crm_outbox`.
- gmail обрабатывается **только внешней автоматизацией chatgpt**, опрос раз в час. сайт не имеет собственного oauth/refresh token. в журнале `crm_operator_actions` **0 подтверждённых отправок** на момент аудита.
- календарь доступен внешней автоматизации chatgpt. прямого двухстороннего sync в сайте пока нет.
- pwa умеет показывать уведомление после разрешения на iphone **при открытой crm**. браузерный push receive + notificationclick подготовлены, но серверная подписка + vapid + dispatch отсутствуют.
- в postgres созданы `crm_automation_runs` и функция `crm_generate_reminders()`: напоминания о просроченных задачах, событиях за 24ч/2ч и high-priority follow-up, с dedup_key. pg_cron установлен, но **расписание не включено**: попытка вызвать cron.schedule заблокирована политикой доступа к подключению. **не считать эти напоминания активными**.
- `sync_jobs` хранит статусы задач из os. не все задания в ней относятся к crm/gmail: фильтровать по провайдеру и scope.
- на dashboard crm v11 отображается реальное состояние, а не обещания.

## целевая архитектура

1. **ingest**: gmail api (oauth read/modify/send), google calendar (oauth events), telegram bot (webhook при явной авторизации), сайт (already website_events), задачи/ручные сообщения. каждое событие снабжено `provider_event_id`, `received_at`, `project_id`, оригинальным source и нормализованным типом. обновления идемпотентны по ID.
2. **queue**: транзакционный outbox в supabase с `job_id`, `idempotency_key`, `status`, `attempt_count`, `next_attempt_at`, `last_error`, `created_at`; атомарное резервирование для worker и экспоненциальные ретраи, max attempts, dead-letter.
3. **intelligence**: текст письма → intent/category/priority → связывание с существующим проектом/лидом → поиск в контексте → draft. модель не отправляет письмо сама. любые данные письма являются недоверенными, защищать от prompt injection. решения модели всегда проверяются явной схемой.
4. **policy engine**: allowlisted действия по типу, контрагенту, цене, договору, календарному конфликту, IP/личным данным. условие `requires_approval` для юридических и финансовых обязательств до явного числового лимита; пользователь разрешил бесплатные подтверждения встреч/бартера только при полном совпадении условий.
5. **execution**: Gmail send reply with message/thread id; Google Calendar events; CRM task updates; website event processing. после API success запись в audit trail, затем уведомление; confirmation only after external provider reports success. предотвращать повторную отправку после timeout через Gmail SENT / draft / provider id.
6. **delivery**: PWA Web Push на iOS 16.4+ для установленной на экран «домой» CRM после permission; VAPID keys **только сервер**, push subscriptions с RLS, device revocation, retry/backoff, доставку вести отдельно от alert creation. Telegram bot как резерв по opt-in, ChatGPT hourly как промежуточный канал.
7. **observability**: worker heartbeat, последний успешный ingest, lag, ошибки, доля обработанных, человеческие approvals, last API errors, алерты. health screen в crm. не маркировать подключение зелёным без настоящего provider auth + успешного test job.

## зависимости и порядок реализации

### этап 1 — данные и надёжность (есть частично)

- сохранять все изменения задач, статусы, архив, связи задач с проектами.
- развивать алерты по календарю, дедлайнам и follow-up с уникальными ключами, без повтора по каждому опросу.
- **включить реальный cron** для `SELECT public.crm_generate_reminders();` каждые 15 минут только через разрешённую настройку supabase scheduler; затем проверить `cron.job_run_details` и строки в `crm_automation_runs`.
- обязательный мониторинг ошибок + защита от ложного «готово».

### этап 2 — собственный gmail + calendar backend

1. создать OAuth Google Cloud с consent screen, разрешёнными redirect URL, scopes Gmail и Calendar (минимально достаточными, проверить верификацию/разрешения Google).
2. добавить серверные `/auth/google/connect`, callback, refresh/rotation и revoke. токены хранить зашифрованными; не в localStorage и не в таблице, доступной клиенту.
3. Gmail watch + Pub/Sub и renewal либо fallback background polling, incremental history ID; дедупликация message IDs. calendar incremental sync token/webhook renewals.
4. безопасное обучение на правилах без «самообучения» на вредоносных инструкциях из внешней почты.
5. тесты: одно новое письмо -> одна запись crm -> один ответ или одно approval -> один audit -> уведомление; повтор webhook -> ничего лишнего.

### этап 3 — реальные push и контроль исполнения

1. сгенерировать отдельную пару VAPID p-256. private в secret store backend, public допустим в клиенте. НЕЛЬЗЯ использовать секрет openai/CRM как VAPID private.
2. HTTPS subscribe/unsubscribe endpoint, аутентифицированный crm session, точная проверка origin, hostname push endpoint, payload size и RLS.
3. server dispatcher от `crm_alerts` с lease/idempotency, доставкой в APNs/Web Push и логи каждой попытки. 404/410 удаляет неактуальную подписку, 429/503 ретраи с backoff.
4. iPhone: установленная через Safari pwa, системное разрешение уведомлений, подписка и рабочий тест именно с **закрытым** приложением; tap deep-links to crm.
5. фолбэк Telegram bot или ChatGPT + дневной digest, настройка тихих часов и критичности.

### безопасность и правила

- текущий логин crm — отдельный пароль/сессия; заменить на полноценную auth систему, включить MFA для админки; разделить server-side service-role и публичный anon key.
- не выкладывать tokens, refresh tokens и секреты в chat, git, HTML, историю SQL editor или клиентские логи.
- хранить минимальные фрагменты переписки/метаданные, ограничить retention и доступ; поддерживать экспорт и удаление.
- внешние e-mail/text не имеют права переписывать policy engine.
- статус `completed` выставляется только после подтверждения от Gmail/Calendar/Supabase, никаких пустых автоматических отчётов.
- оператор может автономно подтверждать бесплатные встречи и полный безденежный бартер, когда условия явно одобрены обеими сторонами; до указания бюджета все финансовые обязательства требуют approval.
- согласовывать NDA, юридические документы, эксклюзивные права, скидки вне утверждённой сетки, расходы, депозиты и изменение уже оговорённой сделки.

## измеримый результат и критерии готовности

- загрузка новых входящих в crm: 95% за 5 минут после появления в gmail, 99% за 30 минут (после native oauth).
- входящее без дубликатов: webhook повторён трижды, а письмо в базе одно, исходящий ответ не дублируется.
- каждое автоматическое действие — запись в журнале и подтверждённый provider id, ссылка и время.
- пользователь получает push на заблокированный iphone с закрытой pwa; разрешения и батарейные оптимизации проверены; нажатие открывает crm.
- отложенные и повторяющиеся задачи порождают алерты ровно по правилам, без бесконечных повторов.
- email/Calendar reconnect и отзыв доступа не ломают задачи, дают ясный статус и прекращают исполнение.
- управляющая панель показывает last run, next run, failure count, backlog, successful sends, pending approvals, external provider connectivity.
- тест с финансовым/юридическим письмом не отправляет ответ без approval; тест с безопасной фактической просьбой отвечает и оставляет аудит.

## внешние действия пользователя (единожды)

- Google OAuth consent (gmail/calendar) и подтверждение требуемых scopes в собственном приложении.
- разрешение уведомлений у установленной pwa на iphone и проверка закрытого приложения.
- при необходимости подключение Telegram-бота и выбор уведомлений (проект/канал/тихие часы).
- установление числового лимита расходов/согласования (по умолчанию ноль).
